# Memory internals

This guide describes Cognee's memory operations and how their features behave. See [architecture](architecture.md) for repository structure and [retrieval internals](retrieval-internals.md) for search strategies.

## Core Workflow: remember → recall (+ improve / forget)

As of cognee 1.x the memory API is the primary surface. All functions are async.

1. **remember()** - Store data in memory. Without `session_id` it runs `add()` + `cognify()` and then `improve()` (`self_improvement=True` by default); with `session_id` it writes to the fast session cache and bridges into the graph in the background.
2. **recall()** - Query memory. Auto-routes to a search strategy unless `query_type` is passed (`auto_route=False` falls back to `HYBRID_COMPLETION`). A `session_id` reads the session cache first and falls through to the graph.
3. **improve()** - Run the self-improvement stages over a dataset: with `session_ids`, bridge session Q&A, agent traces, distilled learnings and user preferences into the permanent graph and apply feedback weights; always, conflict review (on by default, skipped without an LLM) and global context indexing (on by default, `IMPROVE_GLOBAL_CONTEXT_INDEX`). Returns an `ImproveResult` with one `StageResult` per stage (see "IMPROVE: the orchestrator" below).
4. **forget()** - Unified deletion (`data_id` / `dataset` / `dataset_id` / `everything=True` — every dataset the user may delete, and every session the user owns or that belongs to one of those datasets; the session cache is shared by every user and is never pruned by forget, so other users' sessions stay — plus `memory_only=True` to drop graph+vectors but keep raw files, and `clean_history=True` to also delete the caller's own search/recall history; a search that finds nothing after `memory_only` does not mean the data is gone). Every mode removes records and memory, not bytes: LanceDB keeps deleted rows in its fragments until compaction, which rewrites a fragment only once enough of it is deleted, and the embedded graph file has no user-facing compaction, so a byte-level erasure guarantee needs the engine's own compaction/vacuum or a new store. One session on its own: `cognee.session.delete_session(session_id)`, `DELETE /api/v1/sessions/{session_id}` or `cognee-cli sessions delete <id>` remove its Q&A turns, agent traces, session context and improve() watermarks, its Q&A vectors, and its `session_records` / `session_model_usage` rows — the caller's own sessions only. Lessons already distilled from it into a dataset are documents and stay (`forget(data_id=...)`). It raises with `CACHING=false`.

#### Low level operations: add → cognify → search

These still ship and are what the memory API calls underneath. Reach for them to drive one stage in isolation (custom pipeline tasks, stage-level debugging), not for ordinary ingestion or retrieval.

1. **add()** - Ingest data (files, URLs, text) into datasets
2. **cognify()** - Extract entities/relationships and build knowledge graph
3. **search()** - Query knowledge using various retrieval strategies

Note: Using Low level operations over core is useful in the following contexts.
1) Some add()/cognify() options are not accepted by remember(): it routes kwargs through a fixed allow-list (`_ADD_ONLY` / `_COGNIFY_ONLY` / `_SHARED` in `cognee/api/v1/remember/remember.py`) and raises `TypeError: Unexpected keyword arguments` for anything else. Unreachable today: cognify's `chunk_attachment`, and `ontology_file_path` (remember still takes an ontology via `config={"ontology_config": {"ontology_resolver": RDFLibOntologyResolver(ontology_file=...)}}` or `ONTOLOGY_FILE_PATH`); add's `skip_connection_test`; the DLT option `column_value_columns`; and extra cognify `**kwargs` forwarded to the extraction tasks. (`add()` accepts but ignores the web-scraping options `tavily_config` / `soup_crawler_config` / `extraction_rules`; `extraction_rules` works from both via `preferred_loaders={"beautiful_soup_loader": {"extraction_rules": ...}}`, with the `scraping` extra installed; without it the rules are silently ignored.)
2) remember() hardcodes datasets_arg = [dataset_name]: always exactly one. Use cognify for this: cognify(datasets=["a","b","c"]) or datasets=None (every dataset the user owns.)
3) remember() always runs add() first. To rebuild a graph over data already in the DB — after forget(memory_only=True), or with a new graph_model/ontology, cognify() is the only path.
4) add() is like a staging area for cognify(). But remember automatically adds every time.
5) search() packs skills/tools/max_iter/code_query into retriever_specific_config for you. Using recall() you hand-build that dict yourself.
6) prune.prune_system(metadata=True) drops the relational DB (users, tenants, ACLs, the dataset_database registry, pipeline runs, search history.) forget() touches none of that. Full test teardown is prune's job.

`cognee.delete` is deprecated (since 0.3.9, in favor of `datasets.delete_data`); `forget()` is the v1 replacement that unifies the old delete/prune/empty_dataset paths.

Triplet embeddings were removed (SDK-1115). What callers used to reach them stays one release as a deprecated shim that raises a `FutureWarning` naming its replacement, and is removed in the release after: `cognee.memify()` (also at its old path `cognee.modules.memify.memify`) / `POST /api/v1/memify` (use `improve()`, or `run_custom_pipeline()` for your own tasks; named or given tasks still run, a call with no tasks checks the dataset and runs nothing), `cognee-cli memify` (prints the notice and exits: it cannot name tasks), `improve(extraction_tasks=..., enrichment_tasks=...)` and `POST /api/v1/improve`'s `extractionTasks` / `enrichmentTasks` (use `run_custom_pipeline()`; the tasks still run after the stages, as an extra `custom_tasks` stage, on the first pass only), `SearchType.TRIPLET_COMPLETION` (runs as `GRAPH_COMPLETION`), `ImproveResult.memify_run` (the first pass's `custom_tasks` raw return, else `{}`; still serialized as `memify_run`), and `add_data_points(embed_triplets=...)` (ignored). A set `TRIPLET_EMBEDDING` is ignored with a one-time warning. `cognee.modules.memify.run_memify_tasks` is the internal runner the improve stages use, not a public API.

#### recall() vs search()

`recall()` wraps `search()` — its graph path calls the same authorized search — and adds three things: rule-based query routing when `query_type` is omitted (an ordered first-match rule table in `cognee/api/v1/recall/query_router.py`, no LLM call, so auto-routing is free; it only ever picks CHUNKS_LEXICAL for a fully quoted phrase, CODING_RULES for an explicit phrase, CODE (its `ask` operation over the question's identifiers) for a question with code phrasing (`where is … defined`, `what calls …`) right next to an identifier (`parse_config`, `CodeRetriever`, `foo()`), BROAD for a question that opens with `how many` / `total number of`, TEMPORAL for a question scoped to an absolute date behind a time preposition (`in 2019`, `before 1900`, `on 7 November 1867`), or the HYBRID_COMPLETION default — never CYPHER, which stays behind an explicit `query_type`; with a `node_name` filter only a type that applies it (`node_name_scope`), so a quoted phrase, code question or count goes to the default; and retries as HYBRID_COMPLETION if a routed type comes up empty; with a `node_name` filter it picks only types that can apply it, so a quoted phrase runs as HYBRID_COMPLETION with `only_context=True`, LLM or not, and a code question or count as HYBRID_COMPLETION; dataset routing is not recall's, it sits in the authorized search both share, see [retrieval internals](retrieval-internals.md#search-retrieval)), session memory as a searchable source (`scope` = `graph` / `session` / `trace` / `session_context` / `session_first`; with a bare `session_id` a session hit short-circuits the graph search, and `scope="session_first"` asks for that short-circuit explicitly), and normalized results tagged with a `source` key. Use `recall()` for ordinary retrieval. Drop to `search()` when you need the agentic extras as first-class parameters (`skills`, `tools`, `max_iter`, `code_query`), raw `SearchResult` objects instead of tagged entries, or a pinned `query_type` with no router in the path. `node_type` (what `node_name` names: `NodeSet` tags by default, else the named nodes of that graph type and their one-hop neighbours) is on both, and on both HTTP endpoints as `nodeType`, the class name as a string, resolved server-side by `resolve_node_type` (the bare class name of a DataPoint subclass the server ships or imports; anything else, a dotted path or a class a remote cognify rebuilt from a `graph_model` schema included, is a 422); over `serve()` a typed scope with names is refused against a server whose `/openapi.json` lacks the field or cannot be read; with a typed scope the router picks only types that apply a graph scope, so `TEMPORAL` and `CODING_RULES` drop out. Note `search(session_id=...)` only adds session history to the retrieval context — it never searches the session cache as a source; that is `recall()`-only. Full guide: [recall and search](recall-vs-search.md).

## Critical Data Flow Paths

#### REMEMBER / RECALL: Memory API
NOTE: This is how the memory API flow works under the hood; it's read as a flow of data. So remember calls add(), cognify(), and improve(). `remember(data)` → `add()` → `cognify()` → `improve()` (when `self_improvement=True`) `remember(data, session_id=...)` → session cache → background `improve()` bridge `recall(query)` → auto-route to a `SearchType` → `search()` → permission filter → results

Key files: `cognee/api/v1/remember/remember.py`, `cognee/api/v1/recall/recall.py`, `cognee/api/v1/improve/improve.py`, `cognee/api/v1/forget/forget.py`

**A session belongs to one dataset.** Its first write (plain text, a typed entry, or a recall turn) binds it (`SessionRecord.dataset_id`); every later `remember(..., session_id=...)`, plain text and typed entries alike, resolves its target from that binding (`_resolve_entry_dataset`), and an explicit `dataset_id` or a non-default `dataset_name` naming another dataset raises `ValueError` (409 on `POST /api/v1/remember`, 400 on `/remember/entry`); an explicit `dataset_id` needs write permission. A write that finds the session bound elsewhere by a concurrent first write raises too. The write runs inside the dataset's database context, so the turn's Q&A vector (`SessionQAVector_text`) lands in the dataset's own vector store, where its search turns read it for session history; with backend access control on that context takes a dataset queue slot (`DATASET_QUEUE_MAX_CONCURRENT`) and provisions the dataset's databases on first use, so a session write waits while the process is at its dataset cap and raises when the dataset's databases cannot be bound. Vectors written before SDK-1229 sit in the global store, unread; `delete_session` still strips them there.

**`node_set` on session entries.** A typed QA or trace entry (`POST /api/v1/remember/entry`, or `remember(entry, session_id=...)`) may carry `node_set`, the same node-set names `add()` takes and `recall(node_name=...)` filters on; the call-level kwarg is the same thing (`remember(entry, session_id=..., node_set=[...])` fills an empty field and is an error against a different one, and `remember("text", session_id=..., node_set=[...])` pins through the plain-text path — a change for callers that passed `node_set` with `session_id` before, which was silently dropped: tagging the turns of one session differently is now a 409 on the second set). The first write that carries one pins it on the session (an internal session-context row, like the improve watermarks); later writes must repeat it or omit it, and a different set is refused with HTTP 409 (`cognee.SessionNodeSetConflictError`, which names both sets), so one session never spans two node sets. Identify the conflict by that error name, not the status: the remember routes answer other failures with 409 too. A cache that cannot be read or rejects the pin raises `SessionNodeSetUnavailableError` (503), never a 409. An empty list pins nothing. Every input path (the field, the kwarg, plain text, the pin) goes through one rule, `normalize_node_set`: a list of non-blank names, stored sorted and deduplicated; a bare string or a blank name is refused with a validation error (400 over HTTP), never split into letters or stored. Like the call-level `node_set` everywhere else the list is not size-limited. The pin is read strictly: a session whose cache cannot be read is never treated as unpinned, so a pin is refused rather than overwritten and the bridging stages skip that session for the run instead of adding it untagged (the extractors take one strict snapshot per session for both the persist watermark and the pin). The check runs under its own in-process `asyncio.Lock` (not the session turn lock, so a tagged write never waits behind a recall's answer), so the guarantee holds within one worker process; across workers there is no lock today, and two workers taking a session's first write at once can each pin a set, last write wins (readers take the last pin row on every cache backend), so route a session's writes to one worker. A write that repeats the pinned set rewrites the pin row, so the pin's expiry slides with tagged traffic like the session's other rows. `improve()` appends the pinned set to the node set of everything it bridges from the session into the graph — persisted Q&A, persisted traces, and distilled lessons — so a `node_name`-scoped `recall()` sees what the session stored. User preferences deliberately get no node set: they belong to the user, not to one project. The plugins use this for per-project memory (`COGNEE_PROJECT_NODE_SET`); the MCP `remember` tool takes `node_set` too and forwards it on every path; in API mode it probes the server's `/openapi.json` once and refuses a session `node_set` the server's `QAEntry` lacks, instead of storing the entry untagged. Key files: `cognee/infrastructure/session/session_node_set.py`, `cognee/memory/entries.py`; example: `examples/guides/session_node_sets.py`; journey: `cognee/tests/journeys/test_session_journey.py`.

#### IMPROVE: the orchestrator
`improve()` is an explicit orchestrator over an ordered registry of nine stages (`cognee/modules/improve/registry.py:DEFAULT_STAGES`): `feedback_weights`, `persist_session_qa`, `persist_agent_traces`, `extract_agent_context`, `distill_sessions`, `update_user_preferences`, `build_truth_subspace`, `review_conflicts`, `global_context_index`. The first seven need `session_ids`; the last two work on the graph alone. Order is load-bearing (4 feeds 5, 5 feeds 7, 7 runs before conflict review) and a test pins it. `extraction_tasks` / `enrichment_tasks` are deprecated: they run as a `custom_tasks` stage appended after the registry stages, and `node_name`, `data`, `node_type`, `vector_db_config` and `graph_db_config` scope them. Without custom tasks those options are ignored. Either way the call warns with a `FutureWarning`; `None` or an empty task list counts as not given (REST: `null`).

Each stage is a gate plus a call into existing code plus a result mapping — it never owns retries or ordering. `gate()` runs before any LLM or embedding cost and returns a skip reason (`no_session_ids`, `backend_unsupported`, `opt_in_disabled`, `turned_off` (an on-by-default stage switched off by its argument or env var), `personalization_disabled`, `disabled_by_config`, …). `run()` returns a `StageResult` whose `status` reuses `PipelineRunInfo`'s vocabulary — `completed`, `already_completed` (nothing new since the stage's watermark), `errored` — plus `skipped`. Only `persist_session_qa` is `fatal=True` (except for an `AfterRunHookError`: its Q&A is stored); every other failure is recorded as `errored` and the run continues. One failure is run-wide instead: a stage that errors because the LLM budget is exhausted (`LLMPaymentRequiredError`, HTTP 402; `StageResult.budget_exhausted` classifies both a raised error and a `PipelineRunErrored` a stage's pipeline only reported) stops the run, since every later stage would fail the same way — the remaining stages are `skipped: budget_exhausted`. The stage that hit it stays `errored` and so does the run; when it is the fatal stage the run still raises, with `budget_exhausted` instead of `aborted_by_fatal_stage` on the stages it cut off. For the same reason `cognify_session` stops at the first session window whose build fails on the budget and raises `LLMPaymentRequiredError` unwrapped; watermarks of unpersisted windows stay put.

The run resolves the dataset once and hands every stage a frozen `ImproveRunInputs` (user, resolved dataset id, session ids, `ImproveConfig`, adapter `GraphCapabilities`). It holds the per-dataset lock for the whole run, exactly like a pipeline run, so improve, cognify, add and forget on one dataset queue one after another (process-local, like that lock); on top it claims every session id given (scoped by user id), so two improves bridging one session into different datasets queue too. Both are held until the last stage finishes, background included. A background run returns at once and waits inside its task. `run_in_background=True` runs all stages in one anchored task; await it with `await result.wait()`. `ImproveResult` is what every surface returns: SDK, `POST /api/v1/improve` (`response_model`), the CLI (one line per stage), and `RememberResult.improve` / `.improve_error` (MCP reaches improve only through `remember`'s `self_improvement` — `improve` is deliberately not an advertised MCP tool; the advertised tool set is pinned to remember/recall/forget/code_search, with cognify_status registered but not advertised) (an improve failure after a successful cognify no longer marks the remember as errored). Stages that keep a watermark on the improve operation row (conflict review, the global context index) stamp it there; the row is written when the run finishes — deferred to the background task in background mode — with a failed outcome when any stage errored (so a retry is never gated off) and a `noop` outcome when nothing ran — an all-skipped run — so a no-op call never advances the watermark. The `global_context_index` stage reports `already_completed` only when nothing but a search, a recall or a `noop` improve (one that ran no stage) has run on the dataset since its stamp, whatever the pipeline or outcome (so a failed write and a `forget` count too), because its text must not lag the graph; with backend access control off, any other dataset's run counts too. A build reads the dataset's chunks, entities and summaries in one graph call and embeds only the texts that changed (the first build embeds one bucket per document; a changed summary keeps its id, so its old vector is dropped before the write, since the stores keep a conflicting row's stored vector), so its cost per improve grows with the dataset, not with the write; `IMPROVE_STAGES_DISABLED=global_context_index` turns it off, and dataset routing with it. The index follows deletion without a build: a document deletion removes the document's bucket and the dataset's root by their derived ids (`remove_document_index`, on every graph type, since the index nodes carry the build's dataset-level ref, not the document's), because the root names every document. The removal takes the deleted documents as a list, like `delete_data`, so a connector sweep removes thousands of rows' index nodes and routing rows in one round of store writes. The root is then written again at once from the documents that remain (`rebuild_document_index_root`, after the rows are gone in `delete_data` and after the memory delete in `forget(data_id=..., memory_only=True)`): the default method's root is a rendered vocabulary, so this costs one graph read and one embedding of a short text, no LLM, and keeps broad queries routing to the dataset until the next improve rewrites the buckets (their tf-idf text shifts a little with the deletion and waits for the build). It runs only for a dataset that had an index (`remove_document_index` reports whether any of the nodes it removes existed, since once they are gone nothing tells an emptied index from a dataset never indexed, and a never-indexed dataset must stay without index nodes: routing searches it always) and only when every index node left is one the surviving documents derive, the shape `from_entities` writes, so the documents that remain get their root even when none of them has a bucket (chunks but no entities): an `llm`-built index (clustering ids; its root is an LLM summary over bucket summaries that still describe the deleted document) and a dataset whose last document went get no root until their next build. It never fails the deletion: an embedding provider that cannot be reached is a warning, and the root stays absent until the next improve, as before (a root node the failure left behind, written before its text is embedded, is removed again: the build compares text and would otherwise keep it unembedded, and the mirror, which copies that vector, would fail every later build). Feedback-weight application records applied element ids per QA row so a deleted node no longer causes the same feedback to be re-applied on every run; trace persistence and distillation carry watermarks like Q&A persistence already did.

Settings the loop owns live in `ImproveConfig` (env prefix `IMPROVE_`): `IMPROVE_AUTO_ENABLED` (default true; false turns off the automatic improve after `remember()`), `IMPROVE_DEBOUNCE_ENTRIES` / `IMPROVE_DEBOUNCE_SECONDS` (session-path auto-improve fires only after that many new entries or that much time; seconds alone is time-only — the entries default of 1 steps aside — and there is no timer, so the check runs on each `remember()`), `IMPROVE_STAGES_DISABLED` (csv of stage names), `IMPROVE_FEEDBACK_ALPHA` (learning rate, default 0.1), `IMPROVE_REVIEW_CONFLICTS` (default true; an explicit `review_conflicts` argument overrides it), `IMPROVE_GLOBAL_CONTEXT_INDEX` (default true; an explicit `build_global_context_index` argument overrides it, and dataset routing reads the index it builds), `IMPROVE_EFFECTIVE_DATE_KEY` (default `effective_date`, the document metadata source-date key), `DISTILLATION_MODE` (unset or `coding`, read without the prefix and, like the rest, once per process through `get_improve_config()`; see "Coding distillation" below), and the agent-trace windowing of `persist_agent_traces`: `IMPROVE_TRACE_WINDOW_STEPS` (default 0: a session's whole pending backlog is one cognified document; a value caps the steps per document) and `IMPROVE_TRACE_WINDOWS_PER_RUN` (default 0: one run drains the backlog it started with, windows ending at each session's starting step count so steps written meanwhile wait for the next run; a value caps the windows per run). A pass takes at most 10 sessions (`TRACE_SESSIONS_PER_PASS`, a constant) and holds the dataset lock only for that pass. Shared knobs stay with their owners: `CACHING` / `AUTO_FEEDBACK` (cache layer), `PERSONALIZATION_ENABLED`, `DEFAULT_FEEDBACK_INFLUENCE`. `cognee.wait_for_background_tasks()` drains background improves before a script exits; the API server drains them on shutdown. A host application can also decline a single automatic improve before it starts: `cognee.modules.improve.register_auto_improve_admission(check)` registers one async check per process (a later registration replaces it, `None` / `clear_auto_improve_admission()` removes it) that `remember()` awaits on both paths with `user`, `dataset_id`, `session_id` and `session_ids` — only when an improve would otherwise run, and before the session debounce is consulted, so a skipped bridge never spends the window. A returned reason string (`"insufficient_credits"`) skips the improve and lands on `RememberResult.improve_skipped` (also in `to_dict()`); the data is stored either way. The check is fail-open — one that raises, or answers with anything but `None` or a non-empty string, allows the improve — and explicit `improve()` calls are never gated. Frequency weights were removed (no adapter implemented them and nothing read them).

**Coding distillation** (`DISTILLATION_MODE=coding`, no `IMPROVE_` prefix; off by default, made for the Claude Code plugin, SDK-1335). The default stage 4 extracts lessons mid-session, ten traces at a time with no tool inputs and no view of how the task ended, which for coding sessions gives vague lessons, failures without their fix, and stale project state piling up. In coding mode the per-trace hooks in `SessionManager._maybe_extract_agent_context` do nothing, and stage 4 runs `extract_coding_unit_context` (`cognee/infrastructure/session/coding_unit_extraction.py`) over the traces past the shared `TRACE_EXTRACTION_WATERMARK`, each paired by time with its *turn* (the Q&A row whose request it served and whose answer ended it; `cognee/infrastructure/session/coding_turns.py`): every entry carries its event time (`QAEntry.time` and `prompt_time`, `TraceEntry.time`, stamped by the plugin on one clock, by the store when a client sends none), a turn runs from its prompt time (else the previous answer) to its answer, a trace belongs to the latest turn started before it (so a background subagent's late trace stays with its turn), a trace newer than the last answer waits for the next improve, and a trace without a time goes to the newest turn. Positions cannot do this: the plugin's Stop hook is asynchronous, so the next turn's first traces can land before the answer. The whole settled backlog is one extraction pass (a backlog over 400 is walked oldest first in windows of 400, each sealed before the next), so the LLM call count follows the trace text, not the turn count; the `cwd` / `date` / `start_commit` / `end_commit` / `branch` the plugin puts in each Q&A entry's `context` as JSON are read per turn. The traces are split into explore / change / verify parts without an LLM (`cognee/infrastructure/session/trace_phases.py`: tool tables, read-only vs state-changing shell and git commands, inline Python classified by what it writes, imports or runs, scratch paths under `/tmp` / `/var/folders` / `/dev/null` / `$var` not counting; chained commands split on unquoted separators and take the strongest segment; setup commands and other tools inherit the previous phase; blocks merge smallest-into-smaller-neighbour until every part has 5 traces and there are at most 4 parts, or `ceil(n/30)` above 120 traces). The input to the LLM has, per part, in order, EXISTING LESSONS (the session's 40 newest), LESSONS ALREADY IN MEMORY (up to 8 stored lessons, 1,500 chars, from a vector search over the part's paths, error lines, commands and patterns, this session's lessons first, then the dataset's lessons of the same project, the session's pinned node set; 30 s timeout, fail-open, so the section is left out when the search fails), TRACES with tool inputs (a `-- turn k --` header opens each turn's traces; repo-relative path, command, pattern or edit snippets; errors and outputs to 600 chars, redacted), REPEATED ERRORS AND WHAT WORKED (failed traces grouped by tool and first error line and, for a multi-line error, its last line (no error format is parsed; the last line, hashed into the pitfall key, keeps errors that share a generic first line such as a traceback head apart), each paired with what fixed it: the first later success that changed the same file, or for a shell failure the changes made before the first later success that ran the same command, flags and paths aside; the section shows 10 groups, the candidates below cover every fixed group) and FINAL MESSAGE (the request and answer of each turn the input covers); a part over 120,000 chars is split into trace chunks that each repeat every section (a turn's header and FINAL MESSAGE block count only in the chunks that show it, so the cut follows the trace text, not the turn count), extracted in order so each sees the earlier candidates, 10 candidates per call, each naming its turn (`CodingAgentContextExtraction`), and every stored candidate links its turn's Q&A row (`SessionContextEntry.source_qa_ids`). Each fixed error group also stores one deterministic `failure_lessons` candidate (confidence 0.9) opening with `[state-key: pitfall:<tool>:<error-slug>[:<qualifier>]]` (`pitfall:Edit:no-changes-to-make:py`, `pitfall:Bash:cat-illegal-option:cat`), idempotent through the applier's content dedup. The extraction holds a per-(user, session) lock and reads the watermark inside it, so a second trigger on the same unit, sequential or concurrent, extracts nothing; an LLM failure propagates before its window's watermark moves. The stage does not require `AUTO_FEEDBACK` in this mode. Stage 5 then distills with the coding prompts under `cognee/infrastructure/llm/prompts/coding/` (same file names; the default files are untouched), the `Coding*` models in `session_distillation/models.py` (subclasses, so the default schemas do not change), the candidates batched six at a time in turn order with the request and answer of their own turns pinned to each batch (an unlinked candidate is judged against the newest turn), each lesson taking the date and commit of its own turn, one more call when several batches proposed lessons that names the proposals stating the same fact (numbered statements in, groups of numbers out, `session_distillation_merge_system.txt`; the code folds each group into one of its proposals and leaves every other proposal as it was, so the step only removes restatements and a failed call keeps them all), and a writer input that adds `PROPOSED STATE KEY`, a glossary recased from the session's own text (the graph stores `marktaskcommand`, the lesson must say `MarkTaskCommand`) and the compact STYLE line. A writer rejection `already_known` never applies to a keyed lesson: a state key names a replacement and a pitfall key a recurrence to count, so the curator's working statement is stored under the key instead; a rejection counts as the pitfall only when the writer typed it `pitfall` or every member is a failed-trace candidate. Evidence rules then fix the type: a lesson the writer typed `pitfall`, or left untyped with no key of its own, that is backed by a repeated-error candidate is a `pitfall` with that key (a lesson typed otherwise keeps its type and key); a `pitfall` with no failed-trace candidate becomes `change`; only `state` and `pitfall` keep a key. Each accepted lesson is one document, `Lesson-Type: <type>`, `State-Key: <key>` (state and pitfall only), `# Session learning (session <id>)`, the statement, and for pitfalls `(seen in N sessions)` where N is the number of distinct sessions that stored the key in the project (each row carries the list as `seen_sessions`, so the count survives replacement and re-distilling a session never changes it). The `Data` row's `external_metadata` carries `lesson_type`, `state_key`, `session_id`, `session_date`, `git_commit`, `git_branch`, `files` (names the statement mentions, original casing), `seen_sessions` and `seen_in_sessions`, which is what the plugin reads from the dataset listing (SDK-1336), and the same dict in `system_metadata`, the only copy the replacement and the counts read (`external_metadata` is user-writable, so a planted document with lesson keys is never a lesson); the row id is derived from the dataset and the text. After add and cognify (also when only cognify's after-run hook failed, the error raised afterwards), the key's lessons in the same project scope (the dataset's coding lessons with the same node sets besides the `session_learnings` ones, so repositories sharing a dataset do not collide) are reduced to the one with the newest `session_date`, the lesson just stored winning ties and undated comparisons, and two lessons of one run with the same key storing the later one only (`lesson_store.replace_superseded_lessons`, through `datasets.delete_data`; coding mode therefore requires delete permission on the dataset next to write). Unset, nothing reads differently: prompts, models, inputs and documents are the defaults. Guide: `docs/coding-distillation.md`.

The `review_conflicts` stage (on by default) reviews Entity facts using their source documents and dates. An entity is reviewed when its claims name at least two values of one kind (entities sharing a type, or dates under one relationship name) from at least two documents, when two of its chunk statements from different documents give different numbers, dates or codes for one thing, or when it owns a stored conflict. It stores `FactConflict` nodes and per-fact status marks and leaves Entity descriptions as extracted; the hybrid retriever (`HYBRID_COMPLETION`, `TEMPORAL`) shows the explanation of each conflict that names a returned entity, and no entity descriptions. Multiple simultaneous values are not conflicts; fixed attributes remain disputed, while dates can order time-varying values. It needs an LLM and `EDGE_EVIDENCE_ENABLED=true`; re-reviewing a stored conflict also needs a graph adapter that implements `delete_edge_triples` (Ladybug, Neo4j, Turso, Postgres demo — not Neptune, and not community adapters that have not implemented it). Later runs review touched entities, showing only the value groups and statement pairs that gained a fact since the last review (a run that retries a failed entity shows everything), and repair conflicts with missing citations or pending writes; only succeeded improve rows advance the review watermark. An entity whose facts do not fit one review call, even without its list-like relationship names, is not reviewed; the stage counts it in `entities_skipped` and does not retry it. With no usable LLM it is skipped with `no_llm_configured`, so keyless (GLiNER) installs are unaffected. `IMPROVE_REVIEW_CONFLICTS=false` turns it off by default, automatic improve after `remember()` included; an explicit `improve(review_conflicts=True/False)` overrides that per call; switched off either way, the stage is skipped with `turned_off`. `IMPROVE_STAGES_DISABLED=review_conflicts` disables the stage outright. The older `consolidate_entity_descriptions_pipeline` is deprecated.

Key files: `cognee/modules/improve/` (`stage.py`, `stages.py`, `registry.py`, `result.py`, `inputs.py`, `capabilities.py`, `config.py`, `watermarks.py`, `admission.py`), `cognee/api/v1/improve/improve.py`, `cognee/infrastructure/background_tasks.py`, `cognee/api/v1/remember/auto_improve_debounce.py`

The stages below are the Low level operations these call underneath.

#### ADD: Data Ingestion
`add()` → `resolve_data_directories` → `ingest_data` → `save_data_item_to_storage` → Create Dataset + Data records in relational DB

Re-adding a document that already exists (same `data_id`, through `add()`, `remember()` or `update()`'s full rebuild) follows the PATCH rule described under UPDATE below: `node_set` and a `DataItem`'s `label`, `external_metadata` and `node_set` keep their stored values when not passed, clear on an explicit empty value, and are replaced by a value. Content-derived metadata always refreshes; `_cognee.source_uri` takes the new content's location, and new content without one (an upload, raw text) drops the old one. Connector document rows state their full node sets, so a row with none reports `[]` and clears the stored ones on re-sync. A re-ingested row that points at new stored files releases the ones it pointed at, the original and the text derived from it: `forget()` removes the files a row points at, so a file no row points at would otherwise stay on disk.

Key files: `cognee/api/v1/add/add.py`, `cognee/tasks/ingestion/ingest_data.py`

#### COGNIFY: Knowledge Graph Construction
`cognify()` runs two pipelines per dataset (`cognee/modules/cognify/memory_pipelines.py`). First `indexing_pipeline`: `classify_documents` → `extract_chunks_from_documents` → `index_chunks_for_search` (writes the chunk and document nodes and embeds the chunk text, so `CHUNKS` / `CHUNKS_LEXICAL` / `RAG_COMPLETION` / `HYBRID_COMPLETION` answer before extraction; no LLM call; `EARLY_CHUNK_INDEXING=false` or `cognify(early_chunk_indexing=False)` skips the run). Then `cognify_pipeline`: `classify_documents` → `extract_chunks_from_documents` → `find_indexed_chunks` (the same chunks, cut by the same `build_chunking_tasks`; records which the vector store already holds so `add_data_points` does not embed them again) → `extract_graph_from_data` (LLM extracts entities/relationships as structured output) → `build_summary_from_extraction` → `add_data_points` (store in graph + vector DBs). A failed run of either pipeline is rolled back per item (`cognee/modules/cognify/rollback.py`): the documents it stamped complete keep their nodes, edges and stamp, only the unfinished items' writes are removed, so the next cognify re-extracts only those (on `STORAGE_BACKEND=s3` with an embedded graph or relational database, Ladybug or SQLite, only once the run's push has stored its writes: a failure before the push rolls back the whole run, stamps included, since the next process would otherwise skip documents S3 never received); the failure semantics are unchanged (the run is errored, `raise_on_error=True` raises `CognifyFailedError`, `RAISE_INCREMENTAL_LOADING_ERRORS=true` stops at the first failing item). The cognify run opens first and is the one callers follow (its run id, its events); the indexing run works between its start and its tasks under the same dataset lock. `cognee/modules/cognify/memory_status.py` folds both runs into one memory state (`indexing` → `extracting` → `ready`, with the search level), read by `GET /api/v1/datasets/status/memory`, `cognee.datasets.get_memory_status()`, the CLI and recall's warm-up probe, which routes recall to chunk search and appends a `memory_<state>` marker until the graph exists. `update()`'s incremental path refuses a baseline whose chunks were written by a run that never completed, or whose document has no cognify completion stamp (`no_baseline`), so entity-less chunks never seed an incremental update. The summary step is LLM-free by default (`SUMMARY_METHOD=from_extraction`): it joins one line per extracted type, then the chunk's extracted relation texts, so a chunk with no relations gets no summary. `SUMMARY_METHOD=llm` or `cognify(summary_method="llm")` restores `summarize_text`, one LLM call per chunk.

Times are first-class in the default path: the graph prompt asks for points in time as nodes of type `Timestamp` named by their normalized string (`YYYY`, `YYYY-MM`, `YYYY-MM-DD`, `YYYY-MM-DD HH:MM:SS`) and linked by `{verb}_at` edges (`born_at`, `founded_at`, `begins_at`, …). Graph construction (`construct_data_points_and_edges`) turns such a node into a real `Timestamp` datapoint (`precision` records how much was stated; the id derives from the string, so one time is one node) in the same LLM call — no extra pass. Before that call, deterministic `dateparser` hints resolve year-less expressions ("the following 27 April") against the last stated date earlier in the same document and are rendered into the prompt's TEMPORAL_NORMALIZATION_HINTS block (`cognee/modules/engine/utils/temporal_hints.py`; a `custom_prompt` gets no hints); a date the LLM leaves in prose ("23 March 1947") is normalized at construction. A "Timestamp" node whose name still does not parse, or that has outgoing edges, stays an ordinary `Entity`. `update()` shares this extraction, so edits get the same handling.

Key files:
- `cognee/api/v1/cognify/cognify.py`
- `cognee/tasks/graph/extract_graph_from_data.py`
- `cognee/tasks/storage/add_data_points.py`

#### Document structure: where a row sits in its source's tree
A document-mode row (Notion today) may carry a `cognee_structure` json column, `{"ancestors": [{"kind", "id", "name"?, "document"?}, ...]}`, nearest parent first (`dlt_utils.STRUCTURE_COLUMN`, validated by `resolve_dlt_sources._row_structure`, kept in `system_metadata["structure"]`). It is never hashed, so a move keeps the row's `data_id` and runs no extraction; `DOCUMENT_SYNC_VERSION` 3 is the capability gate. add() skips an item whose record is already processed, so `_refresh_row_structure` writes a changed position onto the existing record before add() runs.

`cognify()` runs `reconcile_document_structure` (`cognee/tasks/ingestion/document_structure.py`) as the `after_items_ran` hook of `run_pipeline`: awaited when the run completed and also when items in it failed (reported or raised), ahead of the `after_run_completed` vector compaction, and, like compaction, on a completed run its errors are not swallowed: they reach the caller of `cognify()` as `AfterRunHookError` after the run is already recorded as completed (the remaining datasets of the call still run first, and the error names every dataset whose step failed; in background mode it is logged), and a failure repeats on every cognify of that dataset. With `raise_on_error=False` (`POST /api/v1/cognify` included) nothing is raised: each failed dataset's completed run carries the reason as `after_run_error`. `remember()` still runs its automatic improve and then raises it (with `raise_on_error=False` or in the background it reports it as `after_run_error` on its result instead); `update()` reports it as `after_run_error` on its result, as it does a failed run; improve's session, trace and distillation bridges first advance their watermarks (the data is stored, so the LLM work is not repeated) and raise it after, which records their stage as `errored` (it does not stop the run, not even from the fatal `persist_session_qa`). On a failed run the run's own error wins: a raised one is kept with the hook's error as its `__cause__`, a reported one is returned and the hook's error is logged. It reconciles the whole dataset, not the run's items, without an LLM: `child_of` edges (child to parent) between Document nodes, the parent found by `external_id` within source + `table_name` + dataset, and `StructureContainer` nodes for ancestors without a row (a Notion database or data source; the id includes the dataset). A parent outside the dataset gets no edge, and an edge whose Document node does not exist yet (an empty page has no chunks) waits for it. Nothing is removed until everything is added. Stale edges go through `delete_edge_triples` (Neptune cannot, so there a moved row keeps both parents). On graph-provenance graphs each container carries the source ref of every row beneath it, so `forget()` removes it with its last row; on any other graph the next cognify that still has structured rows does. The pass does nothing for a dataset whose rows carry no structure. `child_of` is bundled as structural in the visualization.

#### Connector sync schedule
A stored connection syncs on a schedule when a sync policy covers it (`cognee/modules/integrations/sync_policy/`, worker opt-in with `INTEGRATIONS_SYNC_SCHEDULER_ENABLED`). Run the API that enables it as one process per database: a slot starts once across processes, but two runs of one connection are kept apart only in-process (`ingestion.exclusive_sync`), so more processes can run a connection twice over one dlt working directory and cursor. Full guide: `docs/integration-sync-schedule.md`.

#### UPDATE: Chunk-Level Incremental Updates
`update(data_id, data, dataset_id)` diffs the new content against the stored processed text (`Data.raw_data_location`) and replaces only the chunks the edits touched: a paragraph-anchored multi-region diff (near-linear for any change shape, including repeated-line-heavy content) finds every disjoint changed span (so edits at the top, middle, and end of a document are three small regions, not one giant one), each span is expanded to chunk boundaries and re-chunked with the document's chunker (TextChunker unless `DEFAULT_CHUNKER` or `update(chunker=...)` names another; same boundary semantics as pipeline chunks, cut against the token budget recorded on the chunks it replaces — every chunk stores `max_chunk_tokens`, so documents stay self-consistent across config changes; legacy chunks without the field fall back to the current config; only a region's last chunk may be under-filled), replaced chunks (plus their summaries, chunk-orphaned entities, and legacy triplet embeddings) are deleted, and only the new chunks run through LLM extraction. Chunks between regions are kept without being re-chunked, so their boundaries and ids cannot drift. Unaffected chunks keep their node ids, entities, summaries, and embeddings; surviving chunks are renumbered so `chunk_index` stays contiguous. Chunk identity is content-derived (`uuid5(doc : sha256(text) : occurrence)`, see `cognee/modules/chunking/chunk_id.py`), so unchanged content keeps its identity across edits. Both incremental and full fallback paths preserve `data_id`. Either path leaves only the current version's stored files under the data root: the previous version's original and derived text are removed once the row points at the new ones, and the files an update staged but did not publish (unchanged content, a refusal, a failure) are removed when it ends. A file that cannot be removed fails the update with `StoredFileNotRemovedError`, also when the new content is already published or a refusal would otherwise have led to the full rebuild: a stored file cognee cannot delete is never reported as a success. Its message opens with the state the document is in (the update was applied; it was not applied; or, on the full rebuild, the new content is stored but the memory is not rebuilt, and running the update again rebuilds it), then names the file and the storage error; nothing removes that file later, so it has to be deleted by hand. A file is removed only once no `Data` row references it (`remove_data_file_if_unreferenced`), so content two documents share stays until the last one lets go, and a file outside the data root (the user's own) is never touched.

Runs under the per-dataset lock with the dataset-scoped database context (multi-tenant-safe). Falls back to the full delete + re-add + cognify flow when preconditions fail (first ingestion, non-text content, pre-v2 chunk ownership, or an unverified graph adapter — verified: Kuzu/Ladybug, Neo4j and the Postgres demo adapter; Neptune falls back); disable with `update(..., chunk_level_diff=False)` or the same query param on `PATCH /update`. Document metadata follows a PATCH rule on either path: `node_set`, and a `DataItem`'s `label`, `external_metadata` and `node_set`, keep their stored values when not passed, an explicit empty value (`node_set=[]`, `label=""`, `external_metadata={}`) clears them, and a value replaces them (`merge_existing_row_metadata` in `cognee/tasks/ingestion/ingest_data.py`; the call's and the item's node sets count together, as their union). Passing any of them forces the full rebuild, since the chunk-level path never touches the row.

Every call that names no chunker uses the deployment's default: the chunker `DEFAULT_CHUNKER` names (registered with `register_chunker()`), else TextChunker. That holds for `cognify()`, `remember()`, `update()`, the CLI (`--chunker` only overrides it), the API, the dry-run estimator, the task-list builders custom pipelines use (`get_default_tasks`, `get_indexing_tasks`, `get_gliner_demo_tasks`) and cognee's own pipelines (session and trace bridging in `improve()`); every public entry point that takes a chunker defaults to None and resolves it once with `resolve_chunker()`, and the helpers below it take the resolved class; `remember()` resolves it before `add()`, so an unregistered name stores nothing. The dlt route alone pins TextChunker, since its rows are not cut. Register the chunker in every process that reads the setting (API workers, MCP server, CLI, scripts): an unregistered name fails every write. `update()` uses the resolved chunker on both paths. The chunk-level path needs the chunker that cut the stored chunks (compared by `chunker_id`): a document holding any other chunker's id is rebuilt in full with the resolved one (`unsupported_chunker`), so the first update after `DEFAULT_CHUNKER` changes rebuilds that document once and later updates are chunk-level again; `cognify()` alone never re-cuts a document it already processed, and an update with unchanged content does not either. What a chunker needs for the chunk-level path (its own `chunker_id` stamped on every chunk, chunks that join back to the document's text) is in the `cognee/modules/chunking/chunker_registry.py` docstring. `register_chunker()` refuses a class with no `chunker_id`, or with the id of another registered or built-in chunker (the code-docs pipeline's `code_docs` included), and "TextChunker" always names TextChunker; never reuse the id of a chunker no longer registered, since documents it cut still carry it and nothing checks; every chunk a chunker yields without an id is stamped with the chunker's own, registered or passed per call, and one yielded with another chunker's id fails the run with `CogneeConfigurationError` (`stamp_chunk`; only chunks being cut are stamped, never stored ones). Chunks stored before cognee 1.5.4 carry no `chunker_id`: TextChunker goes on updating those documents chunk-level, and any other chunker with an id rebuilds such a document once, like any document it did not cut. Example: `examples/guides/custom_chunker.py`; journey: `cognee/tests/journeys/test_default_chunker_update.py`.

## Extension points

### Working with Ontologies
Cognee supports ontology-based entity extraction to ground knowledge graphs in standardized semantic frameworks (e.g., OWL ontologies).

Configuration:
```bash
ONTOLOGY_RESOLVER=rdflib  # Default: uses rdflib and OWL files
MATCHING_STRATEGY=fuzzy   # Default: fuzzy matching with 80% similarity
ONTOLOGY_FILE_PATH=/path/to/your/ontology.owl  # Full path to ontology file
ONTOLOGY_MODE=annotate    # Default: enrich only. strict drops entities with no ontology grounding
ONTOLOGY_REASONING=none   # Default: asserted triples only. owl_rl expands the OWL 2 RL closure (needs `cognee[ontology]`)
```

`ONTOLOGY_MODE=strict` keeps an entity when either its type matches an ontology class or its name matches an individual, and drops the rest (plus their edges). It prunes only the graph — chunk text stays stored/embedded, so CHUNKS/RAG_COMPLETION can still surface dropped entities. It expects an ontology covering the corpus's vocabulary (a small ontology drops most entities; an aggregate dropped/retained count is logged), and an empty/missing ontology file with strict on is a hard error. The mode can also be set per call via `config={"ontology_config": {"ontology_mode": "strict", ...}}`.

The ontology is also used at read time (`ONTOLOGY_QUERY_GROUNDING`, default true, only active with `ONTOLOGY_FILE_PATH` set; `ONTOLOGY_QUERY_GROUNDING=false` turns it off, and there is no per-retriever switch). `GraphCompletionRetriever` (and its COT / context-extension / summary / decomposition subclasses) and `HybridRetriever` look up runs of the query's words — longest first; a lone stopword such as "will" is not looked up — by exact key in the ontology's classes and individuals, the last word also tried singular (`credit exposures` → `CreditExposure`). There is no fuzzy matching, so a misspelled word does not ground. They then (a) pin the matched nodes as exact-score seeds (`brute_force_triplet_search(pinned_node_ids=...)` / the hybrid entity lane), under the deterministic ids cognify wrote them with (`EntityType.id_for` / `Entity.id_for`), and (b) prepend an `## Ontology grounding` block to the context (`"credit exposure" refers to CreditExposure (class); is a RiskMetric`). In the hybrid entity lane the pinned concepts come first and count against `entities_top_k`; a concept the dataset's graph does not hold, or holds with no neighbour inside the `node_name` scope, is not shown. A pinned class is read with its `realizes` edges only (the tables that realize it, not every entity of its type), so a class no table realizes is shown there only through the `is_a` edges of its members that vector search also returned. No LLM or embedding call; the block only accompanies non-empty retrieved context, so "nothing found" stays detectable. Hybrid grounds each query of a batch; graph completion pins seeds only for a single query, so a decomposed question with two or more sub-questions gets no pinned seeds, and with `neighborhood_depth` set it pins none (its neighbourhood projection does not apply `node_name`). The resolver is built as cognify builds it (`ONTOLOGY_REASONING` included) and loaded again when the file changes; a malformed file raises. Ontologies passed per call to cognify, or uploaded and referenced by `ontology_key`, are not used at recall. Module: `cognee/modules/ontology/query_grounding.py`.

Relational ingestion (`migrate_relational_database`, both schema-only and full, and the DLT schema graph) also aligns the technical schema with the ontology when one is configured: each table node whose name is an ontology class's exact key (schema prefix stripped, last word also tried singular, the way a question is grounded; no fuzzy matching, so `production` is not a `Product`) gets a `realizes` edge to that class's `EntityType` node, and the class's own ontology subgraph is written alongside — the business ↔ technical mapping. Every `realizes` edge carries `authoritative` / `owner`, set from the authoritative sources: table name to owner, where every listed table is authoritative. A table is listed bare (matching that name in every source) or qualified: `schema.table` for a non-`public` table of `migrate_relational_database`, `database.table` for a table of a DLT database source (the SQLite file's name or the server database's name; dlt reads one schema, so its table names carry none). They come from `cognify(config={"ontology_config": {"ontology_resolver": ..., "authoritative_sources": {...}}})` or `migrate_relational_database(authoritative_sources=...)`, else from `ONTOLOGY_AUTHORITATIVE_SOURCES` as `table[=owner],…`; a per-call value, `{}` included, replaces the environment. A per-call `ontology_config` without `ontology_resolver` turns the ontology off for that call, so pass the resolver with the sources. A malformed ontology file or a failing lookup makes ingestion raise. The hybrid entity lane sorts authoritative edges first and labels them, so when several tables realize one concept the system of record is what the LLM sees. Module: `cognee/modules/ontology/schema_alignment.py`.

Cognify's own matching closes two gaps: a fuzzy class/individual match on a multi-word string is rejected unless every content token survives into the match (`enterprise customer acme` no longer collapses into `EnterpriseCustomer`), and an entity whose type found no class is grounded in the class its *name* ends with (`Credit exposure to Acme Corporation` typed `financial metric` becomes an `is_a CreditExposure`; the head noun must be the class, so `customer feedback form` is not a `Customer`). The head ends at the first phrase breaker (`of`, `to`, `for`, …), so a class whose name contains one (`LineOfCredit`) is never found inside an entity name. Shared string rules: `cognee/modules/ontology/term_matching.py`.

`ONTOLOGY_REASONING=owl_rl` runs an OWL 2 RL deductive closure (via the optional `owlrl` package, `pip install cognee[ontology]`) over the parsed ontology before the lookup is built, so `owl:inverseOf`, `rdfs:domain`/`rdfs:range` typing, `owl:equivalentClass`, `owl:sameAs` and transitive properties are honoured by matching and subgraph extraction. It is opt-in because the closure is materialised in memory and its cost grows with ontology size. Enabling it without `owlrl` installed raises `OntologyReasoningDependencyError`. Per call: `config={"ontology_config": {"ontology_reasoning": "owl_rl", ...}}` (applies when cognee builds the resolver; a pre-built `ontology_resolver` instance keeps its own setting).

Ontologies uploaded over HTTP (`POST /api/v1/ontologies`, then `ontology_key` on cognify/remember) are kept per user by `OntologyService` (`cognee/api/v1/ontologies/ontologies.py`) in cognee's file storage under the data root: `<user id>/metadata.json` (the index) and `<user id>/<blake2s of the key>.owl`. They go through `get_file_storage`, so they are objects in the bucket on an `s3://` data root and are sealed when `FILE_ENCRYPTION_ENABLED` is on. The store's methods are async. The index is read, changed and written back without a lock, so two concurrent uploads or deletes by one user can lose an entry.

Implementation: `cognee/modules/ontology/`

## Memory features

### Custom Graph Models with Typed Edges
Pass a DataPoint-derived Pydantic model as `graph_model` to `remember()`/`cognify()` and the LLM fills it instead of the generic `KnowledgeGraph`. A field holding a DataPoint (or a list of them) becomes an edge named after the field. Two declarations go further:

- **Typed edge fields** — `list[Edge[Source, Target]]`: the LLM answers flat rows (source/target as identity strings) that cognee resolves against the extracted nodes. The third generic controls naming: omitted = the field name; `Literal["a", "b"]` = the LLM picks one; `str` = free-form (normalized). Declare the edge on the root graph model for relationships with no obvious owner, or on the owning node — endpoints of the owner's own type must then be spelled as strings (`Edge["Person", "Person"]`), which resolve against the owning model and its module. A hand-built `Edge` value that omits `source` falls back to the node declaring it; on a parametrized field the declaring node must match the declared `Source`, or the walk raises.
- **Identity references** — `Annotated[Role, FromIdentity()]`: the LLM answers the identity string of an existing node instead of a nested object. Supported spellings: `Target`, `Target | None`, `list[Target]`, `list[Target] | None` (Annotated anywhere); anything else raises `InvalidReferenceTypeError` at model-build time.

Constraints: every edge endpoint and `FromIdentity` target needs exactly one entry in `metadata["identity_fields"]`; endpoints resolve by **exact type**, so a subclass instance does not resolve where its base is declared; a row that cannot be resolved is dropped with a warning — it never fails the chunk.

Over HTTP (`POST /remember`, `POST /cognify`, `cognee.serve()`) the model travels as the JSON schema from `graph_model_to_graph_schema`: the prompt model's flat shapes plus each class's `metadata` default and two extension keys, `x-cognee-edge` (the endpoint classes of a row-list field) and `x-cognee-from-identity` (the target class of a reference), which `graph_schema_to_graph_model` turns back into the annotations, so a remote cognify builds the same graph as a local one. `cognify()` and `remember()` take that schema dict as `graph_model` too, and the routes forward it as sent: `resolve_graph_model` (`cognee/shared/graph_model_utils.py`) is the one place a schema becomes a class for a run, and a schema it cannot build is a `CogneeValidationError` (400) raised before anything is stored or any pipeline run is created; `remember()` checks it up front and hands `cognify()` the dict unchanged, and under `serve()` the dict is sent as given. The schema-editor DSL (`cognee/modules/graph_models/spec.py`) has no construct for either yet.

Key files: `cognee/shared/llm_graph_model.py` (the LLM boundary, both directions), `cognee/infrastructure/engine/models/Edge.py`. Example: `examples/guides/custom_graph_model.py`. Schema boundary: `cognee/shared/graph_model_utils.py`.

Replacement for the LLM extract-and-summarize step of the default `cognify()` task list. `GRAPH_EXTRACTOR` defaults to **auto**: the LLM path when a usable LLM key is configured (`llm_available()`), the GLiNER demo when none is — so a fresh install with no credentials ingests on local models, and the moment `LLM_API_KEY` is set the pipeline is the LLM one, unchanged. `GRAPH_EXTRACTOR=gliner_demo` / `llm`, or `cognify(extractor=...)` / `remember(extractor=...)` (explicit argument wins over the env setting) pin one regardless of credentials. Resolution happens once, in `resolve_extractor()` (`cognee/modules/cognify/config.py`); when it resolves to `gliner_demo` and `gliner2`/`torch` are missing, it installs the runtime before any work starts (`GLINER_AUTO_INSTALL=false` raises `KeylessExtractorNotInstalledError` instead). The GLiNER pipeline in `cognee/tasks/graph/gliner_demo/` runs one batched local-model pass per chunk batch that builds the `KnowledgeGraph` **and** a deterministic two-line `TextSummary` (kept edges as `head rel tail`, then `type: names`). No `extract_content_graph` / `extract_summary` calls; embeddings in `add_data_points` still run — on keyless setups via the fastembed default (`resolve_embedding_defaults()` in `cognee/infrastructure/databases/vector/embeddings/config.py`: no embedding setting configured + no usable LLM key → `fastembed` / `BAAI/bge-small-en-v1.5`, vector size read from fastembed's model registry; `KeylessEmbedderNotInstalledError` when `fastembed` is missing).

- **Install**: recommended `pip install "cognee[gliner]"` (torch from PyPI: the CUDA build on Linux, for GPU hosts). Without it GLiNER still works: torch is not a cognee dependency (PyPI's Linux torch bundles several GB of CUDA libraries), so LLM-key users never download it, and when a cognify resolves to `gliner_demo` with the runtime missing, `cognify()` awaits `ensure_extractor_runtime()` (`cognee/modules/cognify/config.py`; `resolve_extractor()` itself never installs), which runs `cognee/tasks/graph/gliner_demo/install.py` in a worker thread — the event loop stays free and the pipeline starts only once the runtime imports; concurrent callers in one process or several wait on one install — and it installs the `gliner` extra itself (read from cognee's metadata, so `pyproject.toml` is the only list), with progress logged (step, installer lines, elapsed time): its torch requirement only when no torch build (CPU or GPU) is importable, from `GLINER_TORCH_INDEX_URL` (default `https://download.pytorch.org/whl/cpu`, the only package taken from that index); then the rest, when `gliner2` is missing, from the default index with every installed distribution pinned — a package replaced under a live import would break the running process, so an install that needs to change one fails instead (core pins `huggingface-hub<1` and `tokenizers<=0.23.0`, the ranges transformers 4.x needs, for this). It uses pip, or `uv pip` in uv venvs, under a file lock in `sys.prefix`, and logs a one-line tip to install the extra afterwards. The install thread imports torch and gliner2 before returning (verification, and it keeps the slow first import off the loop). Telemetry: `GLiNER Runtime Install Started` / `Completed` / `Failed`, sent only by the call that installs, with versions, OS/arch, installer, installed packages, duration, and on failure the step and exception class — never paths, URLs, installer output or messages (a custom index is reported as `custom`). Every failure raises `GlinerInstallError` (a `CogneeConfigurationError`) whose remediation is the extra; `GLINER_AUTO_INSTALL=false` raises `KeylessExtractorNotInstalledError` with the same fix. The Docker image runs the installer at build time (`python -m cognee.tasks.graph.gliner_demo.install`, after the exact `uv sync`). A later exact `uv sync` removes the runtime-installed packages (they are not in the lockfile); the next GLiNER cognify installs them again. The model (`fastino/gliner2.5-base-v1`, about 750 MB) downloads on first use; the installer's "about 200 MB to download, 800 MB on disk" is the runtime (CPU PyTorch plus gliner2), not the model.
- **Schema** (closed, resolved per document before chunk extraction): caller `entity_types`/`relation_types` → else OWL classes / object properties of `ONTOLOGY_FILE_PATH` (snake_case of `rdfs:label` or local name, `rdfs:comment` as description) → else the frozen `LABEL_BANK`/`RELATION_BANK`, filtered by one GLiNER pass over a bounded document sketch. Capped at 20 per kind. Explicit labels are only reachable through `get_gliner_demo_tasks(...)` + `run_custom_pipeline(pipeline_name="cognify_pipeline")`.
- **Timestamps on the keyless path**: a span GLiNER labels `date`, `year` or `time_period` that parses as a time (`timestamp_from_text`, prose dates included) is emitted as a `Timestamp` node and becomes a real `Timestamp` datapoint in graph construction, exactly like the LLM prompt's Timestamp nodes; anchored to its chunk by `contains`, with entity edges only where a bank relation (`occurred_on`) fires. A span that does not parse ("the 1960s") keeps its GLiNER label. No hints on this path (no prompt to put them in).
- **LLM-free mode side effects**: a pipeline with no LLM task (the gliner_demo extractor) skips the first-run LLM connection probe but still probes embeddings, per capability — an LLM-free run never marks the LLM check done for later LLM runs. In `improve()`, the text-drafting stages `extract_agent_context` and `distill_sessions` skip with `no_llm_configured`; session and trace persistence still run, and so does `global_context_index`, whose default method counts entities instead of prompting. Separately, with no usable LLM key `recall()` still auto-routes, but only to search types that run without an LLM: retrieval-only types run as they are, the completion types whose single LLM call is the final answer (`HYBRID_COMPLETION`, `GRAPH_COMPLETION`, `RAG_COMPLETION`) run with `only_context=True` and return the assembled prompt, and any other routed type (`TEMPORAL`, which extracts its time window with an LLM) resolves to the default, `HYBRID_COMPLETION` with `only_context=True`. An explicit `query_type` is never rerouted, but with no LLM those three completion types run with `only_context=True` there too. The same `RoutingConstraints` (`cognee/api/v1/recall/query_router.py`) keep `CYPHER` and `NATURAL_LANGUAGE` out of routing when `ALLOW_CYPHER_QUERY` is off. Keyed on LLM availability, not on the extractor. `COGNEE_SKIP_CONNECTION_TEST` stays `false` by default.
- **Constraints**: generic `KnowledgeGraph` only (custom `graph_model` raises), `custom_prompt` ignored, no CLI/HTTP flag (set the env var); `extractor="gliner_demo"` raises with `dry_run=True` and while connected to a remote instance. Long chunks are scanned with overlapping 384-word windows (`batch_extract_long`); schema discovery instead uses one plain pass over a sketch capped at 12,000 characters and 3,000 whitespace tokens. Relation endpoints are matched to entity spans by exact normalized name, then unambiguous containment; unresolved pairs are dropped and counted (`GlinerRunStats`).
- **Remote worker** (`cognee/tasks/graph/gliner_demo/remote/`): `COGNEE_GLINER_TRANSPORT=http|grpc|amqp` plus `COGNEE_GLINER_ENDPOINT` sends the two model calls (the label-bank probe and chunk extraction) to a [gliner_worker](https://github.com/topoteretes/gliner_worker) instead of loading gliner2 here; `ensure_extractor_runtime` then installs nothing. The worker windows chunks itself (`window_words` / `window_overlap_words`, gliner2's `batch_extract_long`; worker `main` at or after 92aba3c, topoteretes/gliner_worker#4 — which caps `window_words` at 1024 and the overlap at half a window, checked here before any request) and receives label descriptions verbatim (`""` included), so the graph matches local extraction; a worker without windowing fails the run (`/readyz` `features`, or a reply's `windowed` flag over gRPC/RabbitMQ). One `RemoteGlinerAdapter` per run, built and readiness-checked in `get_gliner_demo_tasks`; per event loop and endpoint, adapters share the transport, a request budget (`COGNEE_GLINER_MAX_CONCURRENT_REQUESTS`) and a 30 s readiness cache; a loop's transports close when it shuts down (`shutdown_asyncgens`, which `asyncio.run` and uvicorn run). Chunk-level `update()` uses the worker too (`_extraction_step` in `cognee/api/v1/update/incremental.py`). Unavailable (429/502/503/504, unreachable, connect timeouts, gRPC UNAVAILABLE/CANCELLED…, a broker that does not accept the request) retries 7 times with jittered backoff (16–32 s in all, enough for a worker restart) and `Retry-After`; once spent, it — like bad credentials, the wrong model (`COGNEE_GLINER_EXPECTED_MODEL`, or an explicit `model_name`: without one the worker's model is accepted), or an endpoint that is not a compatible worker (readiness that does not answer like one, no windowing) — is latched and fails the rest of the run at once, while a rejected or failed request (an oversized reply included, on every transport) fails only its document. A request sent and left unanswered past `COGNEE_GLINER_REQUEST_TIMEOUT_SECS` (`GlinerWorkerTimeoutError`; over gRPC only this client's own deadline, a proxy's earlier `DEADLINE_EXCEEDED` is retried like an HTTP 504) is not resent, since the worker may still run it: it fails its document after a fresh readiness check, which fails the run instead when the worker is gone. Concurrent callers share one in-flight readiness probe and its outcome. The label-bank probe's sketch is cut to the worker's `max_text_chars`. Settings are environment-only (`RemoteGlinerSettings`, prefix `COGNEE_GLINER_`, same names as the Rust SDK; never per request). gRPC message classes are built from serialized descriptors (`remote/grpc_descriptors.py`, regenerated from `remote/proto/`), not protoc-generated modules, so any protobuf ≥ 5.29 works. Live check: `cognee/tests/e2e/remote_gliner/` (skips unless a worker is configured); unit tests: `cognee/tests/unit/tasks/graph/test_gliner_remote_*.py` (RabbitMQ broker tests need `COGNEE_GLINER_AMQP_TEST_URL`).
- **Demo**: `examples/guides/gliner_demo_llm_free_cognify.py`. Unit tests: `cognee/tests/unit/tasks/graph/test_gliner_demo_tasks.py`.

### Skills (Procedural Memory)
Dataset-scoped `SKILL.md` playbooks agents can discover, load on demand, execute, and improve from run history.

- **Ingest**: `remember(content_type="skills", dataset_name=...)` (folder, file, or inline via `skills_text`/`skill_name`) — ingests into the target dataset (default `main_dataset`; pass `dataset_name` to keep skills separate); re-ingest upserts (deterministic ids). HTTP: `POST /skills`.
- **Discover**: `SearchType.SKILLS` — one vector search over the `Skill_search_text` collection, no LLM, **metadata-only results** (never the procedure body; progressive disclosure). Requires exactly one dataset; skills outside that dataset's scope, inactive skills, and empty-scope legacy skills are filtered out. Missing collection returns `[]`, not an error.
- **Skill gate**: `recall()` runs a deterministic regex gate (`cognee/api/v1/recall/skill_gate.py`); procedural-sounding queries trigger a concurrent SKILLS lookup whose hits are appended tagged `source="skills"`. Additive and fail-safe; only fires when exactly one dataset is targeted. Disable with `SKILL_GATE_ENABLED=false`.
- **Execute**: `SearchType.AGENTIC_COMPLETION` with `skills=[...]` — LLM sees name+description, loads bodies via the `load_skill` tool (12k char cap).
- **Improve**: `SkillRun` records (via `remember()` skill-run entries) feed LLM-drafted `SkillImprovementProposal`s; preview then apply by proposal id (`/proposals` router).

### Code Files (cognify CODE route)
Supported code files (`.py`, `.go`, `.ts`, `.java`, `.rs`, … — the extension list lives on `code_loader`) are recognized at add time through the loader system: the code loader claims the file, stores it under its real extension, and `ingest_data` tags the record with `system_metadata = {"source": "code"}`. Cognify then routes such items down the CODE route, which runs the deterministic enola code graph pipeline per file — typed `CodeSymbol`/`CodeModule`/… nodes with `calls`/`imports`/`has_method` edges, **no LLM calls**.

- **Search**: code is searchable through `SearchType.CODE` only (deterministic graph operations via `code_query`: `query_facts`, `explore`, `traverse`, `find_path`, `impact_analysis`, `insights`, `architecture`, `delta`, plus the agent navigation operations `capabilities`, `search` (BM25 over names, docstrings and paths; tokenizer in `code_search_index.py`), `neighbors`, `subgraph`, `flows` (enola's `flows.json` entry points: list/show/through), `hubs` and `ask` (seeds, flows, one-hop neighbourhood, file:line citations, coverage notes); rejections carry a stable `code`/`param` in the 422 body). Completion/chunk search types (`GRAPH_COMPLETION`, `CHUNKS`, `RAG_COMPLETION`) do not cover code — the route produces no chunks and no embeddings.
- **Diagrams**: add `"diagram": "mermaid"` (or `"dot"`, or `True`) to any `code_query` and the result carries a `diagram` block with deterministic diagram source (nodes shaped by kind, one subgraph per repository, seeds/focus/path highlighted). `{"operation": "architecture"}` is the module-level overview — symbol-to-symbol edges are rolled up into counted module-to-module edges, routes/storage/services hang off their modules — and it draws itself as Mermaid by default. Renderer: `cognee/modules/retrieval/code_graph_diagram.py`; no LLM, no network. Same option over REST (`code_query` on `POST /api/v1/search` and `/api/v1/recall` with `scope=["code"]`) and the CLI: `cognee-cli search "" -t CODE --code-query '{"operation": "architecture"}' --diagram-out arch.html` (`.html` renders Mermaid in a browser, `.svg/.png/.pdf` run Graphviz on DOT, other extensions get raw source; `--diagram mermaid|dot` prints the source in a fenced block).
- **enola version**: installed by default as the pinned `enola-cli` wheel, which puts the binary in the environment's scripts directory; `ENOLA_PATH` always wins. A missing binary raises `EnolaNotInstalledError` with a reinstall hint — nothing is downloaded at runtime. The version pin lives only in `pyproject.toml`. Cognee reads enola's documented snapshot contract (`facts.jsonl`, `insights.json`, `flows.json`, `receipt.json`; `format_version` 1) and rejects a receipt with a format version it does not understand. Fact ids and resolved relation `target_id`s from the writer are used when present; explainer findings become `CodeInsight` nodes with `evidences` edges; a symbol's `doc` prop (its doc comment) becomes the node's `doc` and description; each `flows.json` flow becomes a `CodeFlow` node with `flow_entry`/`flow_stage`/`flow_route` edges to its entry, stages and routes, but only when the receipt lists that `flows.json` among the run's outputs (a release without the flows renderer leaves an earlier run's file in place; a snapshot without docs or flows ingests exactly as before); flows sharing a name in one repo (two services serving `GET /health`) are named after their entry as well, e.g. `GET /health (svc_a/app.health)`, so they stay separate nodes; an unchanged snapshot is skipped only when the repository node also carries the current `CODE_GRAPH_MAPPING_VERSION` (`extract_code_graph.py`; bump it whenever the fact-to-graph mapping changes, so repositories whose code did not change are mapped again); the receipt's provenance/quality block is stamped on the `CodeRepository` node and reported by the `delta` operation. Bumping the pin means re-checking the known answers in `cognee/tests/test_code_graph_e2e.py`.
- **Opt-out per add**: `preferred_loaders={"text_loader": {}}` treats a code file as a plain document (chunking + LLM extraction).
- **Whole repositories**: a local code-project directory or a GitHub/GitLab repository URL passed to `add()`/`remember()` (API: the `raw_data` form field) resolves to ONE `code_repo` manifest that cognify runs through the CODE_REPO route — a single enola pass with cross-file edges, plus the repo's documents as ordinary items. Remote URLs are shallow-cloned under `COGNEE_REPOS_DIR` (default `~/.cognee/repos`). Git LFS is disabled for every git command (`_run_git` in `resolve_repo.py`): an LFS file stays a pointer, and LFS pointers of documents are not ingested. A token passed as `repo_credentials` is sent only to the repository's own origin. `remember(content_type="code")` builds the same graph without the add step. The CODE route is per-file.
- **Several repositories in one dataset**: the dataset is one enola cluster. Its `code_repo` rows are extracted in a single enola run, so the graph also holds the edges between repositories: `reaches_route` from a client call to the route that serves it, cross-repository `calls`/`imports`. The cluster config has no file of its own — its members are the rows themselves (`system_metadata.repo_path`), and the `repos:` config enola needs is rendered from them and piped to `enola --generate /dev/stdin` (a temporary file, removed when enola exits, on Windows). enola writes the cluster snapshot into each member's `.enola-<dataset_id>` (enola's `output.dir`), not the `.enola` a single-repository run uses: a remote clone is shared by every dataset that adds its URL, and a cluster snapshot holds the other repositories' facts. Each member's label is read back from the `repo_label` in that directory's `snapshot.meta.json`. Each row still owns its own repository's nodes. The snapshot is parsed once per load, off the event loop, and shared by every member's tasks (`ParsedSnapshot`). Adding a repository (`remember(content_type="code")`) rebuilds the others from a fresh snapshot — up to `CLUSTER_INLINE_REBUILD_LIMIT` (5) existing repositories; beyond that only the new rows are built inline and the rest are marked for the next `cognify()`, which rebuilds the whole cluster. Deleting one (`forget(data_id=...)`, `datasets.delete_data`) does not run enola — the remaining rows are marked for re-extraction, and the next `cognify()` of the dataset rebuilds them, as after `forget(memory_only=True)`. The enola run over a cluster gets the per-repository timeout times the member count, capped at `CLUSTER_ENOLA_TIMEOUT_CAP_SECONDS` (1 h). Put repositories that call each other in the same dataset; ones in different datasets are never linked. Implementation: `cognee/tasks/code_graph/cluster.py`.
- **Docstrings as memory (code docs pipeline)**: `cognify_code_docs_pipeline(user, dataset=..., extract_entities=False, repo=None, include_modules=True)` in `cognee/memify_pipelines/cognify_code_docs.py` is a memify pipeline over an indexed repository (tasks in `cognee/tasks/code_docs/`). `extract_code_docs` reads the dataset's code graph, reads each documented symbol's docstring from the repository source on the server (Python via `ast`; enola's `doc` prop as fallback: the first paragraph of the doc comment, cut at 300 bytes, which enola 0.5.1 — the pinned release — emits for Python, Go and TypeScript/JavaScript symbols, so those languages get their short docstrings while Python gets the full text; snapshots from releases older than 0.4.30 carry no `doc`) and emits one `CodeDocument` per source file plus one **plain `DocumentChunk`** per documented symbol — text `file:line`, `qualified_name (kind)`, signature, blank line, docstring (a module docstring is `file:1`), deterministic ids (`code_document_id(repo, file)`, content-hash chunk ids). `add_code_doc_edges` then writes a `describes` edge chunk → `CodeSymbol` (module docstring → `CodeModule`) by id through the graph engine, new edges only, and sweeps the documents/chunks (and their summaries) of the run's repositories that the run no longer produced, from the graph and from their vector collections (`DocumentChunk_text`, `CodeDocument_name`, `TextSummary_text`), so a changed docstring replaces exactly its chunk; an unchanged re-run adds no node or edge, but `add_data_points` still re-stores and re-embeds every chunk it is handed. This is the exception to the Search bullet above: the chunks live in `DocumentChunk_text`, so `recall`, `CHUNKS`, `GRAPH_COMPLETION` and HYBRID answer "what does X do" from the docstring and reach the symbol (file, line, callers, flows) in one hop; the code graph's own nodes, hashes and edges are untouched. Embed-only by default (`needs_llm=False` on every task; needs an embedding provider, no LLM key); `extract_entities=True` puts `cognify_code_doc_chunks` first: cognify's `extract_graph_and_summarize` (LLM) over the chunks, one `chunks_per_batch` slice at a time — the whole run reaches each task in one call (every task is a coroutine; a streaming task would hand the sweep a piece of the run and it would delete the rest), so this slicing is what bounds the concurrent LLM requests. By name through the deprecated `POST /api/v1/memify`: `extractionTasks: ["extract_code_docs"]`, `enrichmentTasks: ["add_data_points", "add_code_doc_edges"]` (entity mode: `["cognify_code_doc_chunks", "add_data_points", "add_code_doc_edges"]`); no `data` is needed — the route seeds `extract_code_docs` with `[{}]` instead of projecting the dataset's graph into a memory fragment, as the SDK pipeline does. No CLI entry: `cognee-cli memify` is a deprecated no-op and `cognee-cli improve` takes no task names. Example: `CODE_GRAPH_DOCS=1 python examples/guides/code_graph_example.py`.

### Provenance
Cognee has five provenance mechanisms. They answer different questions and are controlled by three unrelated flags — do not confuse them:

| # | Mechanism | Question it answers | Stored where | Flag (default) |
|---|---|---|---|---|
| 1 | Source stamping | who/which run wrote this node | `source_*` fields on the graph node | `COGNEE_PROVENANCE_MODE` (`lightweight`) |
| 2 | Graph source-refs | which documents own this node/edge (drives `forget()` delete/rollback) | source-ref keys on graph nodes/edges | always on (`cognee/infrastructure/databases/provenance/`) |
| 3 | Audit ledger | tamper-evident history for audits (deletes become `invalidate` tombstones, never row deletes) | `provenance_entries` table, hash-chained | `PROVENANCE_TRACKING` (**false**) |
| 4 | Memory-provenance projection | who can access what (tenant → user → dataset → data + ACL grants) | computed on request from the relational DB (`GET /v1/schema/provenance`) | n/a |
| 5 | Edge evidence | which document chunk supports this graph edge | `provenance_edge_evidence` table | `EDGE_EVIDENCE_ENABLED` (`true`) |

All three table-backed systems (2, 3, 5) identify a document by the same `make_source_ref_key(dataset_id, data_id)` key.

**Audit ledger** (3) is written at the `add_data_points` storage seam (`record_provenance_at_storage`), so every pipeline that stores DataPoints under a dataset scope is covered — cognify, `improve()` enrichment, session bridging, the code-graph route, skills, temporal cognify, custom pipelines. It records the **data item** a batch was stored for and nothing the item produced: one row keyed `"{dataset_id}:data_item:{data_id}"` (`cognee/modules/provenance/tombstones.py` has the key helpers) holding the item's content hash, the acting user's id (never the email), `bundle_id` (the pipeline run id; for cognify the cognify run, also when its indexing run stored the chunks first, `LEDGER_RUN_ID`) and `source_ref_key`. Which node or edge came from which data item is already in the graph (source refs), and a row per node and edge cost about ten times the source text in the always-shared relational database. Rows are never deleted. Storing more batches for an item whose row is live with the same content hash is a no-op; a different content hash archives the old row (`"{id}:v:{last_updated}"`) and versions the live one with `metadata["delta"] = {"content_hash": [old, new]}` (`revision_history` surfaces `delta` / `content_hash`) — an incremental `update()` states the new hash itself (`record_data_item_content`) last, after it publishes the row and retires the decisions the edit left without their fact, never before the publish, so a publish that fails leaves the ledger on the old content. A batch stored for an item whose row is already live on that content stops at a plain read (`data_item_is_recorded`) and never takes the lock all ledger writes share. Every path that deletes a data item — `forget()` / `datasets.delete_data` per item, a dataset delete, the DLT orphan sweep — writes one `invalidate` tombstone (`prov:Invalidation`) on that row, from `(dataset_id, data_id)` alone, and writes it last: after the `Data` row was removed (and, for a single item, checked to be gone), so a tombstone always means the document is gone and a delete that failed earlier leaves the row live. Whatever removes only an item's memory keeps the document and writes no tombstone: `forget(memory_only=True)`, a DLT source purged for re-emission, and the rollback of a failed pipeline run. The row stays live for as long as the document is stored, so the delete that finally removes it is the one the ledger records. A later write resurrects a retracted row with the tombstone kept in its version history. With tracking on, a ledger write or a tombstone that fails raises: the storing task fails and its run is rolled back, an update whose ledger write fails raises with the edit complete (content published, decisions retired), and running the same update again records it (it finds the content unchanged and states the hash), and a delete whose tombstone could not be written fails after the document is gone — deleting the same id again (`status: "not_found"`) writes it, while a dataset delete cannot be repeated, so its rows then stay live. While `PROVENANCE_TRACKING` is off, which is the default, the ledger is not used at all (`cognee/modules/provenance/tracking.py`): nothing is recorded, a delete does not look for a row to tombstone, so a ledger nobody turned on can neither slow nor fail a delete, and the read surface answers with that reason instead of reading (HTTP 409 on every route but `/status`, exit code 1 on the CLI), because "valid, 0 rows" from a ledger that is off would read as a verified one. Rows recorded earlier are served again once it is back on; a document deleted in between keeps its live row. Read surface: `cognee-cli provenance verify|stats|history|entry|export|anchor` and `GET /api/v1/provenance/{entry,history}/{key}`, `/verify`, `/statistics`, `/export` (JSONL, chain order), `/status`. There is no lineage or referential-integrity command: a data item row has no lineage beyond its own history, and its only links are to its previous versions, which `verify` already covers (the manager keeps `get_lineage` / `check` for ledgers written before this). HTTP reads are ACL'd by the dataset in the key (`get_authorized_dataset(..., "read")`), except for superusers, who read any dataset's rows, a deleted dataset's included (its ACL went with it); ledger-wide walks without `dataset_id`, unscoped keys, and anchoring are superuser-only. `verify_chain(dataset_id=...)` checks each of the dataset's rows against the checksum stored at its predecessor chain position; `get_statistics` splits `live_entries` / `archived_entries` and counts live tombstones only. External anchoring (`cognee/modules/provenance/anchors.py`): with `PROVENANCE_ANCHOR_KEY` set, `anchor()` HMAC-signs the chain head into `PROVENANCE_ANCHOR_PATH` (default `{system_root}/provenance_anchors.jsonl`) and `verify_anchors()` catches a ledger that was rewritten *and* re-chained — the one tamper a self-contained chain cannot see. Integration test: `cognee/tests/integration/test_provenance_ledger_round_trip.py`; journey (mock LLM, update, every delete path and the failure cases): `cognee/tests/journeys/test_provenance_ledger_journey.py`.

**Edge evidence** (5) is captured in memory during `add_data_points` and bulk-written once per data item (`EDGE_EVIDENCE_FLUSH_THRESHOLD`, default 10000, forces an earlier flush for huge documents). Search with `include_references=True` returns it as structured `EvidenceReference` objects. Rows are ignored at read time when their pipeline run did not complete or their document is gone (a failed run's rollback detaches the rows of the documents it keeps, `keep_completed_items_evidence`, so those stay readable), and swept when a document is deleted or its memory dropped with `forget(memory_only=True)`. Scope: only edges extracted from document chunks — `improve()` enrichment, session bridging, and the code-graph route record no evidence yet (`evidence_kind` is the extension point). Implementation: `cognee/modules/provenance/edge_evidence/`.
